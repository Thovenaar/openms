# Offline profile and character development

## Schema 8

`profile-validation.js` is the structural save authority. Schema8 retains the schema5 instance/AP/SP/social domains and schema6 pet/mount state, replacing schema7's single `freeMarket` return with source-defined typed saved-location slots:

| Domain                            | Durable contract                                                                                                                                                                                                                                                                                                               |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Inventory and equipment           | Instance records `{uid,id,count,slot,owner,flags,expiresAt}`; five category capacities in `inventorySlots`. Positive inventory positions and negative equipped positions are validated against original templates. Multiple stacks of one template are valid; duplicate instance UIDs are not.                                 |
| Character presentation and vitals | `gender`, `appearance:{skin,face,hair}`, `baseMaxHP`, `baseMaxMP`; equipment-derived maxima are recalculated separately from base vitals.                                                                                                                                                                                      |
| Cash                              | Bounded credit/points/prepaid balances, locker instances, commodity-SN wishlist and persisted gift envelopes. No native button creates payment funds.                                                                                                                                                                          |
| Monster Book                      | Card-ID counts capped at five and the selected cover; opening or inspecting the Book grants nothing.                                                                                                                                                                                                                           |
| Skill macros                      | Five saved macros, each containing three skill positions, a bounded name and shout preference. Macro editing is not learned-skill acquisition.                                                                                                                                                                                 |
| Social                            | Reciprocal friends/invitations and mirrored party, guild, alliance, family and Messenger state, plus blacklist and party-search preferences. These refer to actual browser-local character IDs.                                                                                                                                |
| Settings                          | BGM/SE volume and mute, chat mode/height, quest-helper IDs/auto/open, game-option permissions and HP/MP alert thresholds.                                                                                                                                                                                                      |
| Pets and mount                    | Existing schema6 pet records and mount level/EXP/tiredness are preserved; migration grants no pets or mounts.                                                                                                                                                                                                                  |

Each value is `null` or a safe integer map ID from0 through999999998; `FREE_MARKET` also excludes910000000. Values are map IDs, not portal objects or nine-digit strings. |

`remainingAp` is a nonnegative safe integer independent of `remainingSp`'s exactly ten nonnegative safe-integer pools. `skills` contains at most 4096 canonical numeric-ID records `{level,masterLevel,expiresAt}`. Learned and master ranks are separate; `level <= masterLevel` applies only to the catalog-aware mastery-gated books, not universally. Expiration is `null` or a nonnegative safe epoch-millisecond integer.

Migration validates legacy root keys and retained values before conversion. Version1 receives recovered default bindings; v1/v2 receive ten zero SP pools, no learned ranks and default chat preferences; pre-v4 receives zero AP. Versions1–4 convert aggregate stock into individually identified, template-limited stacks and assign equipped templates unoccupied authored slots; base vitals preserve old maxima and new cash/book/social/macro domains start empty/default. Version5 receives empty pets and default mount state. Versions1–6 receive all typed saved-location slots as `null`; version7 validates its exact `savedLocations:{freeMarket}` shape, preserves that value as `FREE_MARKET` and adds the other slots as `null` before schema8 validation. Existing character progress, AP/SP, bindings, quests, location and preferences survive. Larger legacy capacities remain browser compatibility, not purchased expansion. Missing metadata, conflicting equipment slots or unrepresentable stack expansion reject without replacing durable data. Migration grants no skills, points, levels, jobs, cash, memberships or past visits.

The key inventory comes from Cosmic `SavedLocationType`, shared by `profile-domains.js`, script compilation and runtime admission. Supported authored `saveLocation(type)` stores the current numeric map; `peekSavedLocation(type)` reads without consuming, while `getSavedLocation(type)` consumes a present slot and returns its map. An absent slot returns−1 to the authored script. Destination preparation and the state-changing NPC turn use the existing atomic profile/location authority; a typed slot does not itself authorize an arbitrary destination or server script. See [authored travel](ingame-portals.md#authored-npc-travel-and-world-tour).

`settings.chat` retains original mode 1–3 and integer height 26–507. Original `008d4a6d` writes mode at `DAT_00bebf9c+0x54`, reads height at `+0x5c`, and uses 70 outside that range; rendering adds 2 when height is divisible by 13 without changing the saved value. See the retained [chat-mode consumer](ghidra-client-corrections/fidelity-chat-modes.txt). New helper settings are `{ids:[],auto:true,open:true}`; saved alert thresholds are integers 0–19. GameOpt permissions gate the corresponding local interaction; `allowGame` has no offline minigame consumer.

Ten SP pools and learned/master/expiration records use authorized Cosmic GMSv83 server semantics (`AbstractCharacterObject`, `AssignSPProcessor`, `Character`). Original Skill.wz and executable consumers remain presentation/input authority. Neither source is original Nexon server code or a Windows-runtime comparison.

Normal Stat-window AP allocation is implemented through `CharacterDevelopment.spendAp`: STR/DEX/INT/LUK spend one point for one stat; HP/MP require the native warning and catalog/job-aware growth, update base vitals and recalculate equipped maxima. Admission rechecks life, available AP, supported job and caps in the locked draft. Sidebar edits remain explicit development policy, not earned allocation or advancement. See [AP provenance](ghidra-client-corrections/minimap-provenance.json) for the earlier AP/SP distinction; that artifact predates normal allocation.

## Atomic ownership

The durable and temporary memory implementations live together in `profile-store.js`: `ProfileStore.memory(profile)` does not open IndexedDB. `await store.commitProfile(transform)` accepts a synchronous transform of an isolated mutable draft; the transform returns nothing. The whole resulting profile is validated and cloned again, so a caller retaining the draft cannot mutate the persisted or published candidate.

The transaction is single-flight. A concurrent profile edit or binding save rejects `save-busy`; the accepted operation waits for an earlier flush. Later flush, reset and teardown operations drain the accepted transaction through the existing operation promises. `commitKeyBindings` uses this same path. Durable writes retain strict IndexedDB transaction completion, revision/generation compare-and-swap, timeout/abort handling and cross-tab conflict rejection. A failed transform, validation or durable write cannot publish its candidate. Success publishes all fields together in one notification. Failure restores an equal mutable profile before reporting the error; save revision is not advanced by validation failure.

`store.profileTransactionPending` is synchronous from acceptance until completion. The current **plain** profile graph is bounded-deep-frozen during this interval: previously obtained nested references cannot bypass exclusion, and `structuredClone(store.profile)` remains supported. Success installs the isolated mutable candidate; failure installs an equal mutable clone of the prior profile. Callers must reacquire `store.profile` after **every atomic transition**, including failures; old root/nested references remain frozen. Do not retain a profile root inside a long-lived name renderer or service.

`ProfileStore.commitCharacters(stores, transform)` extends this boundary to a bounded set of actual local character handles. It acquires all exclusions before waiting, validates all drafts and global item/gift UIDs, and enforces reciprocal/mirrored social membership across the complete affected cohort. Durable participants are compare-and-written in one IndexedDB transaction; all roots are installed before observers run. A peer trade or gift is not two independent saves. Memory-only participants stay isolated from durable characters.

### Admission is not publication

Ordinary refusals should occur before durable transaction admission. Inventory moves/equipment changes first run on a detached profile; appearance resources are prepared without replacing the live actor, then current ownership/profile identity is checked and the transform runs again inside `commitProfile`. Trade similarly applies both offers to detached drafts before acquiring `commitCharacters`, then rechecks participants, same-map ownership, instance identity, restrictions, quantities, capacity, balances and fees inside the lock. A capacity refusal leaves items/mesos unchanged and releases the terminal room's pending gate; it is not a storage failure that should poison a later room.

Authored NPC callbacks preview their turn on detached data and reexecute state-changing turns in the locked draft. Shops revalidate the selected instance and quote after the native prompt and again in the transaction. Cash and social services own their own local semantic admission. No preview, prompt, drag image or read-only snapshot authorizes durable mutation.

Cancellation discards an unaccepted carry, editor draft, shop prompt or trade proposal. It does not reverse a previously committed NPC callback or completed purchase. Once durable work is accepted, scene replacement/teardown drains it rather than cancelling half the transaction. Reload restores committed profile domains, not transient windows, dialogue VM continuations, trade offers, preview outfits or unsaved form values.

### Required integration gates

Before mutations—not merely at the subsequent `markDirty` call—Main excludes physics/field/mob/reactor authority, location/settings checkpoints, item/quest/skill actions, map/scenario replacement and reset admission while `profileTransactionPending`. Rendering and inspection remain live. Elapsed wall time while paused must not become later physics catch-up. Audio controls may change audio-owned settings, but checkpointing them into the profile waits until the lock is released. Ordinary synchronous gameplay keeps the existing `markDirty` API outside transactions. Frozen data is the fail-before-mutation backstop, not a replacement for usable input admission.

## Persistent development service

`new CharacterDevelopment(store, catalog, hooks)` exposes `await edit(patch, {jobPreset = null} = {})`. The ordinary patch accepts only name, level, job, EXP, HP/MP and base maxima, STR/DEX/INT/LUK, meso, fame, AP, ten SP pools, learned records and key bindings. Arbitrary inventory/equipment replacements remain inadmissible. The patch is snapshotted before waiting. Validation includes nonnegative safe-integer AP, HP/MP maxima, level 1–200, EXP below `experienceRequired(level)` (or zero at level 200), original job membership from `catalog.ui.coverage.skillCoverage.playerBooks`, and each record's learned/master rank within `catalog.ui.skills[id].maxLevel`.

Job changes retain learned records; availability is separately derived by the skill owner. No AP/SP/job gifts or destructive rank normalization occur. EXP thresholds still use the explicitly provisional offline progression policy, not a newly recovered original EXP table. Persistent development editing is separate from agent sandbox editing.

`InGameSystems` wires `owner.hooks.onProfileEdit(patch, options)` to this service and `owner.hooks.onLearnSkill(id)` to normal skill allocation. The persistent **Edit character** form uses typed native browser controls in the inspection sidebar, outside the original raster gameplay plane: name text, integer scalar inputs including AP, a catalog-backed job selector, ten labeled SP pools, and advanced learned-record add/remove/rank/master/expiry controls. Blank expiry means `null` (permanent); numeric expiry is epoch milliseconds. **Apply changes** commits only changed fields together; **Discard** restores the current profile projection. Unsaved form values survive unrelated profile refreshes. Pending edits disable mutation controls and expose saving/error status. These are explicit local development controls, not a recovered original character-editing feature.

Normal learning remains in the Skill window and spends the applicable points through `SkillSystem`; editing a learned record is not normal allocation. Learned skill carry uses `owner.beginBindingDrag(event, { type: 1, id }, null, { source: layer, path: template.iconPath })`, with the leased UI surface as its source. Catalog visibility does not imply learned ownership or an available cast controller.

### Development job loadouts

The Character section's **Stage preset → Apply staged preset / Apply changes / Discard** transaction previews original equipment and ammunition as well as skills and shortcuts. The adjacent Apply button and the form's Apply changes submit the same draft. Staging runs on a detached clone and grants nothing to the live profile. Discard throws away that preview. Apply carries only the selected job identity alongside the scalar/skill patch; it does not accept caller-supplied item records. An unchanged utility preset reports that its values already match and makes no persistence request. See [online preset and summon replacement recovery](original-resource-audit.md#character-presets-and-development-authority) for the shared runtime fix and authoritative server proof.

This is deliberately generous **development policy**, not original advancement or earned progression. All four base attributes use the existing `AP_POLICY.statMaximum` of 32767; base and current HP/MP use the existing visible 30000 cap. These limits come from the authorized Cosmic server-reference/local AP policy, not a new claim about the original Windows runtime. The job level policy remains Cygnus 120 and other jobs 200. Mesos, AP/SP balances and unrelated save domains are not overwritten.

The weapon choices are original `Character.wz:Weapon/<eight-digit ID>.img` entries: warrior sword1402000, spear1432000, mage wand1372000, bow1452002, crossbow1462001, claw1472000, dagger1332000, knuckle1482000, gun1492000, and Aran polearm1442000. Beginner Legend instead uses the unrestricted polearm1442012, beginner Evan the unrestricted wand1372005, and ordinary beginners/special books sword1302000. Original catalog availability and prepared combat metadata are required; a missing item does not create a replacement. The class branches select a useful weapon, not all mutually exclusive mastery weapons simultaneously.

Armor selection is bounded to packaged, visible, ordinary original templates in the hat, coat/overall, pants, shoes, gloves and cape positions. It prefers job-specific armor, then the highest eligible authored level, then lowest item ID; ordinary strict `wearRequirements` filters candidates without coercing malformed original metadata. Cash, timed, quest, unique and trade-blocked candidates are not granted. Shared `equipInventory` admission remains authoritative, including original slots/job restrictions and overall/pants or two-handed/shield conflicts. Displaced equipment, including cash overlays covering new gear, moves into real inventory rather than being deleted. Existing usable instances are reused; upgrades, owner, flags and identity survive. Insufficient capacity rejects the entire preset.

Original `Item.wz:Consume/0206.img`, `0207.img` and `0233.img` supply bow arrows2060000, crossbow arrows2061000, Subi stars2070000 and bullets2330000. The shared native-compatible ammunition selector maps weapon families; the preset supplies at least one authored stack's worth of permanent compatible ammunition, respecting learned rechargeable capacity. A job change that lowers that capacity splits excess owned rounds into additional valid stacks without losing quantities. Special skill-only item costs, summons, mounts, combo/form state, cooldowns and server-only skills remain ordinary admission requirements.

Retained original-client evidence is [weapon coverage](ghidra-client-corrections/reported-r3-weapon-coverage.json): weapon families00460aa0, ammunition008c7f3c/00949b5d and authored required level005daf30. Job-mask wear admission is native004f2cee; the existing inventory authority also uses explicitly labeled Cosmic stat/fame and conflict semantics. These references do not imply execution of the original Windows client.

Preset Apply sets `CharacterDevelopment.pending`, validates the detached complete candidate, prepares its real avatar/combat resources through the same appearance hooks as inventory equipment changes, then rechecks profile equality and current ownership before atomic publication. Failed preparation, lost ownership or a changed live profile releases the candidate appearance and publishes no grants or scalar edits. Normal gameplay remains excluded during that pending operation. The original appearance publishes only after the durable transaction succeeds.

### Development monster search

Play → **Spawn monster · development only** searches the packaged original monster catalog by case-insensitive name or ID. Search text is capped at120 characters; the catalog is bounded to16384 entries and the DOM shows at most200 matches with an explicit refinement message. Selection itself has no gameplay effect. Only the **Spawn selected monster** button requests the development admission hook.

The UI contract is `monsterCatalog() → [{id,name}]`, `spawnMonster(id) → Promise<{ok,reason?,id?}>`, and `snapshot.developmentSpawn:{available,reason}`. The button is disabled while paused, loading, preparing another spawn, lacking a field or rejected by the gameplay admission owner. Async feedback is discarded after control teardown or field replacement. Catalog artwork, preparation, entity-count limits, map ownership and destruction belong to the actual field lifecycle—not to the selector or a renderer-only clone. The admitted monster must be a normal combat/drop/quest participant; no grant or spawn is an online mutation.

The current catalog indexes327 original templates from the packaged map closure. A field admits at most128 development spawns and4096 total combat entities. Prepared original animation/audio and skill capacity are acquired before the live grounded actor is published. Spawned actors use normal combat, drops and quests, are one-shot rather than authored respawn placements, and are destroyed on field teardown without entering the durable save.

Focused regressions cover detached staging, atomic gear/vitals publication, retained instances, inventory-full rejection, lost-ownership artwork release and ordinary wear eligibility. Selection now calls the same `wearRequirements` authority as normal equipment use; the original string-valued `1082192/reqLevel` cannot win coercive ranking and abort a whole preset. The executed `development-loadout-spawn` scenario exercises real stage/discard/apply, original name/ID search, pause refusal, spawn click and ordinary combat at800×600. [Integrated validation](validation.md#gameplay-corrections-and-authority-proposal) retains the build identity, captures and final hover-contrast check.
